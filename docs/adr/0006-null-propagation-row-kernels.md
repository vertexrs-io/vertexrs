# ADR-0006: Null Propagation Convention for Row-Mode Kernels

| | |
|---|---|
| **Status** | proposed |
| **Date** | 2026-06-16 |
| **Supersedes** | — |

## Context

Row-mode kernels generated by `node!(name = src.row(|x| ...))` compute a scalar function over
every element of their inputs. When one or more input columns carries an Arrow `NullBuffer` (i.e.
the column is nullable), the engine must decide what the derived output column's validity bitmap
should be, and whether the kernel closure needs to know about nulls at all.

Two coherent conventions exist:

1. **Skip-null execution**: the map closure is called only for non-null positions; null positions
   in the output are left as their default value and marked null in the output bitmap. This means
   the closure is only invoked `n − null_count` times.

2. **Compute-all-rows, mask-after**: the map closure is called for every position, including null
   ones. The output bitmap is computed independently by combining the input bitmaps, then attached
   to the fully-computed output vector. Junk data may sit at null positions in the output buffer.

The choice determines whether `Option<T>` must appear in closure signatures, how kernel fusion
interacts with null positions, and how much overhead null propagation adds to the hot path.

## Decision

VertexRS row-mode kernels use the **compute-all-rows, mask-after** convention (option 2 above).

Concretely:

- The kernel closure always receives a raw `T`, never an `Option<T>`. The user-written function
  body does not need to handle nulls.
- After the map pass, the output `Node<T>` has its `validity` field set by calling
  `Node::combine_validity` over the input columns' `Option<NullBuffer>` references. This computes
  the bitwise AND of all input validity bitmaps (a position is valid in the output iff it is valid
  in all inputs).
- When all inputs are non-nullable (`validity == None` for every column), `combine_validity`
  returns `None` immediately and no bitmap allocation or computation occurs. This is the zero-cost
  fast path for the common case.
- Null positions in the output buffer may contain junk (whatever the kernel computes over the
  corresponding null input value). Consumers must consult the validity bitmap before reading any
  output value.

The bitmap merge is attached via the new `Node::with_validity` builder chained onto
`Node::new_with_deps` in the macro-generated code.

## Alternatives considered

- **Skip-null execution (Option A)** — closures would need `Option<T>` signatures or a
  `SkipNull` wrapper, breaking backward compatibility and complicating kernel fusion. The savings
  (skipping `null_count` kernel invocations) are rarely large enough to justify the added
  complexity, especially since SIMD lanes are wasted anyway when the iteration becomes conditional.
  Rejected.

- **Propagate `Option<T>` through closures explicitly** — makes the user's closure signature
  nullable-aware (`|x: Option<f64>| x.map(|v| v * 2.0)`). Verbose and incompatible with the
  declarative, zero-boilerplate design goal (ADR-0005). Rejected.

- **No null propagation in row mode; require explicit `fill_null` before use** — simpler macro,
  but silently drops null information in derived columns. Violates the Arrow semantics contract
  (ADR-0001) and the AC2 acceptance criterion. Rejected.

## Consequences

**Positive:**
- Kernel closures remain simple scalar functions with no nullable-aware syntax; the pipeline macro
  handles null bookkeeping transparently.
- The zero-allocation fast path (`None` when all inputs are non-nullable) means existing
  non-nullable pipelines pay no cost from this change.
- Consistent with how Arrow compute kernels themselves work (e.g. `arrow-arith` applies bitmaps
  after arithmetic, not during).
- Kernel fusion (ADR-0003) is unaffected: fused single-pass kernels still operate on raw values
  and can combine their input bitmaps in one merge step at the end of the fused chain.

**Negative / trade-offs:**
- Junk data sits in null positions of output buffers. Any code that reads output values without
  consulting the validity bitmap will silently operate on garbage. This is standard Arrow behaviour
  but must be documented clearly on all output accessors.
- For very high null-count columns, computing the kernel over null positions wastes cycles. This
  is acceptable at Phase 2; a skip-null optimisation path can be added as a hint annotation in a
  future phase without breaking API.
- Downstream consumers of `Frame::get::<T>(name)` receive the raw payload slice with no null
  masking applied. They must call `Frame::get_validity(name)` separately to obtain the bitmap.
  This is consistent with Arrow's split-buffer model but differs from a `Vec<Option<T>>` mental
  model.
